Critical — Page-breaking / silently broken behaviour
C1
Toggle logic fails on first click — menu never opens
Functionality JavaScript
Line 152

Problem: The toggle compares menuItems.style.display === 'block'. On the very first click the browser has never set an inline style on that element — the display is controlled by the stylesheet rule display: none. The inline style property is therefore an empty string "", not "none", so the condition "" === 'block' is false, and the code sets display = 'block' — which appears to work. But on the second click the condition "block" === 'block' is true, so it correctly hides. Then on the third click the inline style is now "none", not "", so the condition "none" === 'block' is false, and it opens again. Subsequent toggles work correctly from here — but this is only coincidentally correct after the second interaction and will confuse any developer who later removes the CSS rule.

Root cause: Relying on inline style comparison instead of checking the computed style or using a CSS class.

// Broken — fragile first-render assumption
menuItems.style.display = menuItems.style.display === 'block' ? 'none' : 'block';

// Fix option 1 — read computed style
const computed = window.getComputedStyle(menuItems).display;
menuItems.style.display = computed === 'none' ? 'block' : 'none';

// Fix option 2 (preferred) — CSS class toggle
menuItems.classList.toggle('menu-items--visible');
High — Incorrect rendering / wrong styles applied
H1
CSS selectors header h1 and header p match nothing
Structure CSS
Lines 50–63

Problem: The CSS rules on lines 50–63 target header h1 and header p — descendants of a <header> element. However, the HTML uses <div class="header-container">, not a <header> tag. The selectors therefore match no elements at all, meaning the gold colour, large font-size, text-shadow, and white tagline colour are never applied.

Impact: The h1 renders in the browser default black, and the tagline p in default black — both invisible against the wheat background.

/* Broken — targets non-existent <header> element */
header h1 { color: #FFCC00; font-size: 3em; ... }
header p  { color: #FFFFFF; ... }

/* Fix — match the actual element used */
.header-container h1 { color: #FFCC00; font-size: 3em; ... }
.header-container p  { color: #FFFFFF; ... }
H2
background-color overridden by shorthand background on the same element
CSS Functionality
Lines 39 & 47

Problem: .header-container first sets background-color: rgba(255,255,255,0.1) (semi-transparent white), then later in the same rule block sets background: wheat. The shorthand background resets all background sub-properties including background-color. The semi-transparent declaration is therefore dead code and the element always renders solid wheat, making the comment "Semi-transparent white" misleading and the first line wasted.

/* Line 39 — dead, overridden immediately */
background-color: rgba(255, 255, 255, 0.1);
/* Line 47 — shorthand resets everything above */
background: wheat;

/* Fix — remove the dead declaration */
background: wheat;
H3
Redundant <h2>Our Menu</h2> duplicates the button label
Structure Accessibility
Lines 136–137

Problem: The <section> contains both an <h2>Our Menu</h2> and a <button>Our Menu</button>. This creates a visual and semantic duplicate. Screen readers will announce "Our Menu" twice. The original code used the <h2> as the interactive element; when the button was added the heading should have been either removed or repurposed as a section title distinct from the button.

<!-- Current — both say "Our Menu" -->
<h2>Our Menu</h2>
<button class="menu-btn" onclick="toggleMenuItems()">Our Menu</button>

<!-- Fix — keep heading as section label, rename button -->
<h2>Our Menu</h2>
<button class="menu-btn" onclick="toggleMenuItems()">Show Menu Items</button>
Medium — Structural / behavioural issues, accessibility gaps
M1
Inline onclick event handler — tight coupling & CSP violation risk
Functionality Structure
Line 137

Problem: Using onclick="toggleMenuItems()" directly in the HTML attribute mixes behaviour with structure. Any Content Security Policy (CSP) that disallows unsafe-inline will silently block the handler — the button becomes a dead element with no error visible to the user. It also makes the code harder to maintain and test.

<!-- Broken pattern -->
<button onclick="toggleMenuItems()">

// Fix — attach listener in script
document.querySelector('.menu-btn')
  .addEventListener('click', toggleMenuItems);
M2
No charset meta tag — character encoding undefined
Structure HTML
Line 3 (missing)

Problem: The <head> contains no <meta charset> declaration. Without it the browser sniffs the encoding, which can cause special characters (smart quotes, em-dashes, accented letters) to render as mojibake. The HTML5 spec requires <meta charset="UTF-8"> as the first child of <head> for security and correctness.

<!-- Fix — add as first line inside <head> -->
<meta charset="UTF-8">
M3
body grid overflows: height: 100vh with no overflow control
Structure Functionality
Lines 18–21

Problem: The body is a 2-column grid with height: 100vh. When the menu items are revealed the left column content can exceed viewport height, but the body does not scroll (overflow not set). On small screens or when many items are added the content will be clipped below the fold with no scroll affordance.

/* Fix */
body {
    min-height: 100vh;   /* grow if content exceeds viewport */
    height: auto;        /* remove the fixed constraint */
    overflow-y: auto;
}

Low — Accessibility, best practice, minor improvements
L1
Button has no aria-expanded attribute — inaccessible toggle state
Accessibility
Line 137

Problem: The <button> controls a collapsible list but carries no aria-expanded attribute. Screen readers cannot convey to keyboard or assistive-tech users whether the menu is currently open or closed.

<!-- Fix -->
<button class="menu-btn" aria-expanded="false"
        aria-controls="menuList" onclick="toggleMenuItems()">
  Show Menu Items
</button>
<ul class="menu-items" id="menuList">...</ul>

// And in JS:
const btn = document.querySelector('.menu-btn');
btn.setAttribute('aria-expanded',
  btn.getAttribute('aria-expanded') === 'true' ? 'false' : 'true');
L2
.image-container is a purely decorative <div> — missing role or aria-hidden
Accessibility Structure
Line 147

Problem: The café image is loaded as a CSS background-image on an empty <div>. Screen readers will announce this as an empty element. If the image is meaningful, use an <img> with alt text. If it is decorative, add aria-hidden="true".

<!-- Fix for decorative image -->
<div class="image-container" aria-hidden="true"></div>

<!-- Or replace with semantic img for meaningful image -->
<img src="..." alt="Interior of Roast Toast Coast Café"
     class="cafe-photo">
L3
External font loaded over HTTP with no fallback verification
Functionality Performance
Line 8

Problem: The Bogart font is fetched from fonts.cdnfonts.com. If the CDN is unavailable or the URL changes the entire site falls back to generic sans-serif with no visible error. Additionally, there is no font-display: swap directive, so the browser may show invisible text (FOIT) during the font load.

@font-face {
    font-family: 'Bogart';
    src: url('https://fonts.cdnfonts.com/...') format('woff');
    font-display: swap;  /* Add this — prevents invisible text */
}
L4
No viewport meta tag — page not mobile-responsive
Structure Accessibility
Line 3 (missing)

Problem: Without <meta name="viewport"> mobile browsers render the page at a desktop-scale zoom level, making the two-column grid illegible on phones. This also affects Google's mobile-first indexing.

<!-- Fix — add after charset meta -->
<meta name="viewport" content="width=device-width, initial-scale=1.0">
